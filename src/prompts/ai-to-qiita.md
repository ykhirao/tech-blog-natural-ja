# AI が書いた日本語技術記事を、Qiita の技術記事らしく直すプロンプト

生成AI に書かせた文章を、**生成AI以前(2020年8月)の Qiita 技術記事の分布に
近づける**ための指示。目標値はすべて実測値。

書き換える相手は「AIっぽさ」ではなく、**読みにくさ**。
実測すると、世間で「AIっぽい」とされる特徴の多くは的外れだった(末尾参照)。

## 目標値(実測)

| 指標 | AI以前の中央値 | 2026年の平均 | 直す方向 |
|------|--------------|------------|---------|
| burstiness(文長のばらつき) | **-0.234** | -0.281 | 上げる |
| 文長の変動係数 | **0.620** | 0.575 | 上げる |
| 漢字割合 | **17.4%** | 23.4% | 下げる |
| 体言止め率 | **15.5%** | 8.3% | 上げる |
| 太字/千字 | **0**(半数が0) | 3.17 | 減らす |
| 箇条書き割合 | **0**(中央値) | 22.1% | 減らす |
| 読点/文 | **0.52** | 0.90 | 減らす |
| 平均文長 | **34.3字** | 38.3字 | やや下げる |
| 段落あたり文数のCV | **0.529** | 0.469 | 上げる |

## そのまま使うプロンプト

```
次の技術記事を、読みやすい日本語に直す。内容は変えない。事実・数値・
コード・固有名詞は一字も変えないこと。変えるのは文のリズムと表記だけ。

## 1. 文の長短に落差を作る(最優先)

いまの文章はおそらく、すべての文が同じくらいの長さで並んでいる。
これが読んでいて眠くなる最大の原因。

- 20字以下の短い文と、50字を超える長い文を意図的に混ぜる
- 目安: 文長の変動係数 0.62 以上(AI以前の技術記事の中央値)
- **短くするだけでは直らない。** 短文ばかりに揃えても均質は均質のまま。
  長い文はもっと長く、短い文はもっと短くして、落差を作る

## 2. 体言止めを戻す

AI が書いた文章は体言止めがほぼゼロになる。30文に1文(全体の3%)程度を
体言止めにする。ただし使いどころがある。

- 定義・言い換え: 「NetFlow は、シスコ社が開発したトラフィック情報を
  収集するための技術。」→ 用語の初出で、段落の冒頭に置く
- 操作の完了: 「モデルのトレーニングを実行。」→ 手順の列挙中
- 結果の提示: 「計測した結果は以下のとおり。」→ 表やコードの直前
- 感想の言い切り: 「ここは正直、面倒だった。」→ 段落の末尾

**「短く切る」と思い込まない。** 実測では体言止めの文が直前より短いのは
36%だけで、平均はむしろ長い(27.6 → 32.7モーラ)。長い説明を最後まで
書いて言い切る用法が主流。

## 3. 漢字をひらく

目標は地の文の 17〜20%(いまはおそらく23%以上)。

ひらく語の例:
  出来る → できる / 為に → ために / 事 → こと / 物 → もの
  行う → する(文脈による) / 及び → と / 尚 → なお
  下さい → ください / 頂く → いただく / 但し → ただし

漢語を和語に言い換える:
  実施する → する / 使用する → 使う / 確認する → 確かめる
  必要となる → 要る / 可能である → できる

## 4. 読点を減らす

目標は1文に0.5個程度(いまはおそらく0.9個)。
読点が2つ以上ある文は、たいてい2文に分けられる。

  × 設定を変更した後、再起動が必要になるため、手順に注意が必要です。
  ○ 設定を変更したら再起動が要る。手順に注意。

## 5. 装飾を減らす

- 太字: AI以前の記事は**半数が太字を1つも使っていない**。
  1記事に2〜3箇所まで。本当に重要な1点だけ残す
- 箇条書き: 文章で説明できることは文章で書く。
  箇条書きは「並列で、順序がなく、3つ以上」のときだけ
- 見出しを全部「結論形」に揃えない。それ自体がテンプレートに見える

## 6. 段落の厚みを揃えない

AI は全部の段落を同じ文数で刻む。書くことが多い段落は長く、
少ない段落は1〜2文で切り上げる。均等は怠慢。

## 7. 消していい定型

- 「本記事では〜について解説します」だけの前置き段落
- 「〜と言えるでしょう」「〜することが可能です」→「〜できます」
- 「いかがでしたでしょうか」
- 中身のない「まとめ」(本文の繰り返しなら消す)

## やってはいけないこと

- 事実・数値・コード・固有名詞を変える
- 書いていないことを足す
- 文体を変えるために内容を薄くする
- 全部の文を短くする(1の理由による)
```

## 直したあとに機械で測る

プロンプトだけでは直ったか分からないので、lint で確かめる。

```bash
npx textlint --rulesdir ./src/textlint --config .textlintrc.json 記事.md
npx textlint --config .prhrc.json --fix 記事.md   # 表記は自動修正できる
```

指摘がゼロになるまで直す必要はない。**指摘は疑いであって、
直すかどうかの判断は書き手が持つ。** 固有名詞の反復のように、
正当な理由があるなら残してよい。

## 実測で覆った通説

直す対象を決めるとき、思い込みで禁止語リストを作ると外れる。

| 通説 | 実測 |
|------|------|
| 「しましょう」はAIっぽい | 元記事の実測では**減っていた**(0.114→0.034/千字) |
| 文が長いのはAIっぽい | 平均文長の伸びは**AI以前からの傾向**で説明できる |
| 体言止めの多用がAIっぽい | 逆。**ゼロなのがAI的**(19.0% → 8.3%) |
| 体言止めは短く切る | 直前より短いのは**36%だけ**。平均はむしろ長い |
| 「最後に」「まさに」はAI語 | coji氏の実測では**人間の日常語**(誤検知の63%) |
| 文頭の反復はAIっぽい | 逆。人間93% vs AI 41%で**人間の方が多い** |

## Goodhart の法則

lint を通すことが目的化すると、新しい定型を生むだけ。
指標は下限であって目標ではない。数値を満たすために不自然な短文を挟めば、
今度は別の意味で機械的になる。
