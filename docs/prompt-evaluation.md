# 変換プロンプトは効くのか

[`src/prompts/ai-to-qiita.md`](../src/prompts/ai-to-qiita.md) を実際に適用して、
参照分布からのズレが縮むかを測った記録。

結論: **効く。ただし1回目は失敗した。** 失敗の仕方に再現性のある教訓がある。

- 実施日: 2026-09-14
- 測定: `scripts/style_distance.py`(AI以前の Qiita 6,952本を参照分布とする)
- 題材: AI に書かせた想定の技術記事1本(CI/CD パイプラインの設計判断)

## 結果

| 版 | ズレ | 備考 |
|----|------|------|
| before(AI が書いた想定) | **0.556** | 体言止め0%、文長のばらつき p5 |
| after1(1回目の書き直し) | 0.512 | **失敗**。文を短くしすぎた |
| after2(2回目) | **0.398** | 成功。before から **28%改善** |

指標ごとの推移:

| 指標 | before | after1 | after2 | 中央値の位置 |
|------|--------|--------|--------|------------|
| 平均文長 | p22 | **p10** ↓ | **p50** | 34.3字 |
| 文長のメリハリ | p16 | **p10** ↓ | **p62** | -0.234 |
| 文長のばらつき | p5 | p10 | **p62** | 0.620 |
| 体言止め率 | p0 | p24 | p0 | 0.155 |
| 漢字割合 | p95 | p95 | p95 | 0.174 |

## 1回目の失敗: 「直せ」と言われて短くした

after1 では、平均文長が p22 → **p10 に悪化**した。文長のメリハリも p16 → p10 と
下がっている。ズレ全体は 0.556 → 0.512 とわずかしか縮まらなかった。

原因ははっきりしている。**全部の文を短く切った。**

プロンプト自身に「短くするだけでは直らない。短文ばかりに揃えても均質は
均質のまま」と書いてあるのに、書いた本人が守れていない。

これは coji 氏が観察した現象と同じ:

> 「リズムが単調」と指摘されたAI（私です）は、文を短く切る方向に直したんです。
> (中略) 平均56±22.5の均質さが、平均27±11.9の均質さになっただけ。

**同じ失敗が再現した。** AI は「直せ」と言われると一方向に整えてしまう。

## 2回目: 長い文を意図的に混ぜた

after2 では、短い文はそのままに、長い文をさらに長くした。

> ビルドが遅い。(7字)

> 変更の影響範囲が広いときほど待ち時間が伸びていき、手元では次の作業に移れない
> まま結果を待つことになるので、生産性に直結する問題になっていました。(70字)

これで平均文長が p50、文長のばらつきが p62 に戻った。
**落差を作ることが要点で、短くすることではない。**

## 検証の途中で見つかった違反

書き直しの過程で、**プロンプトの禁止事項を自分で破っていた**。
機械的な検査をしていなければ見逃していた。

1. **数値の捏造**: 「並列度を1から8まで変えながら」と書いたが、
   元記事にその情報はない。文を長くするために創作していた。
2. **主張の追加**: 「テスト1本あたりの実行時間が揃っていない環境では
   頭打ちになる」という一般論を足した。これも元記事にない。

どちらも「書いていないことを足す」の違反。修正後、数値の消失・追加は
ともにゼロになった。

**教訓**: 文を長くしようとすると、AI は情報を創作して埋める。
変換後は必ず数値と固有名詞の差分を機械的に確かめる。

```bash
# 変換前後で数値が変わっていないかの検査
python3 -c "
import re,sys
b=set(re.findall(r'[0-9]+[%％]?', open(sys.argv[1]).read()))
a=set(re.findall(r'[0-9]+[%％]?', open(sys.argv[2]).read()))
print('消えた:', sorted(b-a) or 'なし'); print('増えた:', sorted(a-b) or 'なし')
" before.md after.md
```

## 直らなかったもの

| 指標 | 状態 | なぜ |
|------|------|------|
| 漢字割合 | p95 のまま | 「並列度」「実行時間」など、ひらけない技術用語が多い |
| 体言止め率 | p0 | after1 では p24 まで戻せたが、after2 で長文化を優先して失われた |
| 段落文数のばらつき | p4 | 段落の厚みを変える指示が弱い |

~~**漢字割合は技術記事では下げにくい。** 専門用語は漢語が多く、
ひらくと逆に読みにくくなる。~~

**訂正**: この説明は実測で反証された([domain-differences.md](domain-differences.md))。
専門用語の密度が高い分野(Python/ML)と低い分野(Mobile, Infra)の差は 0.03 しかなく、
同じ分野内で時代差 0.05 が出ている。全5分野で例外なく上昇していた。

漢字率の上昇は専門用語ではなく、**地の文そのものが漢語寄りになった**ため。
語彙分析でも「設計」「検証」「運用」といった漢語が増え、「色々」「とりあえず」
といった和語が減っている。つまり漢字率は**下げられる**。

## この検証の限界

- **1本だけ。** 題材を変えれば結果は変わる。統計的な主張はできない。
- **書き直したのは Claude(私) 自身。** プロンプトを書いた当人が適用しているので、
  第三者が使ったときに同じ結果になるかは分からない。
- **元記事も私が作った。** 実際に AI が書いた記事ではなく、
  「AI が書きそうな文章」を模したもの。
- **ズレが縮む = 読みやすい、とは限らない。** 指標を満たすことと
  読みやすさは別物(Goodhart の法則)。after2 が実際に読みやすいかは、
  人間が読んで判断するしかない。

## プロンプトへの反映

この検証を受けて、プロンプトに以下を追記した。

- 「長くする側の具体例」を入れた(短くする例しかなかった)
- 変換後に数値の差分を機械検査する手順を入れた
